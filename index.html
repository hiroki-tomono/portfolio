自己紹介

エンジニア歴10年超、Rails API 開発が主軸のWebエンジニアです。React / Next.js、AWS・Terraform まで担当します。教育系プラットフォームで5年以上、性能改善(集計を36秒→2秒)や新機能の設計を担い、自社プロダクト Mogupick も2名で立ち上げました。

Rails API の設計から性能改善、AWS の構築まで

バックエンドは、Rails API の設計・実装から、実行計画を読んだ性能改善、MySQL のデッドロックの調査まで一通り自分で担えます。本番のモニタリングから見つけた遅い API を、クエリの書き換えやインデックスの使い分けで改善し、36秒かかっていた集計を2秒に短縮しました。フロントエンドは React / Next.js(TypeScript)で画面の実装からメジャーアップデートまで、インフラは AWS を Terraform でコード管理し、デプロイの自動化まで構築しました。Stripe Connect による決済の設計・実装や、Solid Queue / Sidekiq を使った非同期処理の実装も経験しています。

AI駆動開発の実践と開発フローへの組み込み

Claude Code を設計・実装・テストコード作成・レビューの各工程で使い、業務フローに合わせたスキルを約30本整備しています。Notion・Sentry の MCP(外部ツール連携)と gh コマンドを組み合わせ、仕様書の作成、設計書のレビュー下書き、Sentry の障害調査、Sidekiq の失敗ジョブの整理、脆弱性チケットの起票を Claude Code から行えるようにしました。教育系プラットフォームの案件では、結合テストケース作成などのスキルをチームに展開しています。

設計の合意形成、レビュー、障害対応

教育系プラットフォームの案件には2021年から参画し、5年以上契約が続いています。他メンバーの Pull Request を1,100件以上レビューしてきました。チーム全員で設計する「モブ設計」では議論を主導することが多く、設計方針を変えるときは、論点と却下した案を文書にまとめ、PdM(プロダクトマネージャー)やチームと合意してから進めています。障害時の影響範囲の調査のように手間のかかる作業も自分から引き受け、原因と再発防止策をポストモーテムにまとめてチームに共有しています。

遅い API を自分で見つけて改善(2024〜2026)

状況
目立った問い合わせがなくても、本番のモニタリングでは、生徒数の多い校舎で一部の API の応答が数十秒から数分に達していました。
行動と判断
  • Datadog APM で見つけた遅い API は自分で起票し、実行計画とボトルネックのクエリを分析
  • 校舎の個別メッセージ分析 API は、サブクエリの結合を1本の集計クエリに書き換え
  • 校舎タイムラインの学習記録 API は、生徒1人を指定して呼ばれたときも校舎全体の記録を走査していたことを特定。対象の生徒数に応じて使うインデックスを切り替える形で修正
  • インデックスの指定を外してデータベースの判断に任せる案は、過去に誤ったインデックスが選ばれて指定を入れた経緯があるため採用せず
成果
個別メッセージ分析 API は、2,953件の集計にかかる時間が36秒から2秒に。99パーセンタイルで301秒かかっていたタイムライン API は、走査する範囲を生徒1人分に抑えました。画面が速くなったという校舎からのお礼も、CS 経由で届いています。

頻発する MySQL のデッドロックの解消(2022)

状況
学習記録を取り込む非同期ジョブで、デッドロックが頻発するようになっていました。
行動と判断
  • 調査を引き受け、InnoDB のロック情報から、既定の分離レベル(REPEATABLE READ)で取られるギャップロックが原因と特定。調査結果はチームの Discussion にまとめて共有
  • 根本の原因は MySQL 5.7.12 のバグで、本来はバージョンアップが望ましいと調査で整理。ただし本番 DB の更新は影響範囲と準備が大きく、すぐには行えないため、短期策を選択
  • 分離レベルを READ COMMITTED に変えるのは、問題のトランザクションだけに限定。ほかの処理の振る舞いを変えないため
  • 変更で起こりうる読み取りのずれ(別トランザクションの更新が見える)は、対象レコードの排他ロックを先に取ることで防止
成果
デッドロックを解消しました。2023年には、負荷試験で別のジョブにデッドロックが大量に出た際も、ロック情報からユニークインデックス更新時のロック順序の競合が原因と特定し、排他ロックの事前取得で対処しています。

タグの論理削除の設計と段階リリース(2026)

状況
オペレーターは使わなくなったタグを整理したいのに、手段は物理削除しかありませんでした。物理削除するとメッセージの宛先の参照が失われ、過去の一斉メッセージが見えなくなります。
行動と判断
  • プロポーザルに論点と却下した代替案を理由付きで整理し、PdM と合意してから着手
  • 関連レコードも削除する案は、影響箇所は減るものの、データを残すという目的と合わないため採用せず。関連は残し、参照する側で除外する方針に
  • 削除済みのタグは名前の先頭に「[削除済]」を付ける方式に。名前をそのまま残すと、過去のメッセージの画面で有効なタグと誤解されるため
  • 変更範囲が広いため4フェーズに分け、DB の変更も独立した Pull Request に。機能フラグで本番の挙動を変えずに段階的にマージし、確認してから一本化
成果
2026年6月に論理削除へ一本化し、過去のメッセージを残したままタグを整理できるようにしました。
その他の実績
  • 外部の教材事業者向け連携 API の開発と、OpenAPI 定義・外部向けドキュメントの整備、サービス間 API へのトークン認証の導入を主導。LTI(学習ツール連携の標準規格)や Google Classroom との連携機能の実装にも参加

  • 生徒数の増加で長時間化していた学年の一括更新バッチを、activerecord-import による分割コミットに変更して短縮
  • CircleCI で変更差分に応じてテストと RuboCop を省略する仕組みを改善し、判定できないときは全件実行する安全側の設計に変更。失敗したテストだけを再実行できる設定も整備
